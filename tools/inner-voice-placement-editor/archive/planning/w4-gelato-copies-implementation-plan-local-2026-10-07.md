# W4 and W4.1 Gelato Copies: Implementation Plan

Status: adversarial review passed; ready for execution. No workflow or application code changed.
Date: 2026-10-10

## Goal

Add separate Gelato copies of W4 and W4.1 for the new 8 x 8 inch, 32-inner-page book. Keep the current Lulu workflows and old orders working. The Gelato copies will own Gelato PDF assembly, quote and order submission, status updates, and sibling-group handling. Shared book rendering, page assets, approvals, job tracking, and admin status views should continue using existing project paths where they fit.

## Design

Create two new n8n workflows from the current, verified Lulu exports:

1. `docs/n8n-workflow-files/repo-centric/workflows/w4-GELATO-Print_Fulfillment.repo-centric.json`, with intake path `w4-gelato-print-repo`.
2. `docs/n8n-workflow-files/repo-centric/workflows/w4.1-GELATO-Sibling-Aggregation.repo-centric.json`, with intake path `w4-1-sibling-aggregation-gelato-repo`.

The new workflows get distinct names, webhook paths, production gates, approval scopes, and Gelato API calls. Keep existing Lulu workflow exports and live workflows unchanged. Reuse existing W3 manifests, shared workflow-job telemetry, renderer inputs, and PDF QA helpers when they meet Gelato's one-file requirements. Do not copy unrelated W0-W3 workflows.

Use the frozen book config as the routing source. Add Gelato as an allowed provider with provider-specific print settings in a new book config version. Preserve the current Lulu version for rollback and existing orders. Define exact contract fields: config and normalized manifest carry `provider`, `productUid`, `innerPageCount`, `expectedPdfPageCount`, and numeric `bookConfigRef.version`. Keep Gelato API `pageCount` distinct from PDF page count. Retain current Lulu print settings in Lulu's provider branch. Route `lulu` to existing W4/W4.1 paths and `gelato` to new copies. Apply Lulu fallback only to this book's config version `1`, or to an older manifest with no config ref when its order row has an existing Lulu assignment. Fail closed on other missing provider values and all unknown values. Test both legacy forms, missing provider on config version `2`, and unknown provider. For W4.1, reject groups whose children disagree on provider, product, page count, or destination.

## Acceptance criteria

- Two separate Gelato workflow copies exist with independent names and webhook paths. Current Lulu exports remain unchanged.
- Book config routes new Gelato orders from a frozen provider value; old manifests continue through Lulu.
- Only identifiable legacy orders may use Lulu fallback. New or unknown provider states fail closed.
- W0 explicitly selects and freezes the published Gelato config version for new orders; existing orders retain their frozen config and provider assignment. Missing config version fails closed, and inactive v2 publication does not shift v1 defaults.
- Supported V2.1 and V3 manifests resolve through their matching validators; legacy in-flight orders are durably assigned to Lulu before v2 routing is enabled.
- W1.1 validates every frozen manifest and dispatch gate before claiming; provider assignments are write-once, claims are transactional and all-or-none for sibling groups, and rejected orders remain recoverable without provider crossover.
- W1.1 and the Gelato workflow copies share one idempotent submission record and key. Lease recovery releases only claims proven not to have reached Gelato; ambiguous submissions reconcile before replay.
- W4 Gelato submits a single 35-page combined print file for the confirmed 32-inner-page product after quote validation.
- W4.1 Gelato preserves one-to-one child item mapping and blocks unsafe mixed groups.
- Automated testing can only create explicit Gelato drafts. Paid submission requires Gelato-specific environment gate and order or group approval.
- Status, tracking, cancellation, recovery, and admin views work for Gelato without confusing Gelato IDs with Lulu IDs.
- W4.1 child mappings persist atomically; recovery can find provider-accepted orders after local persistence failure.
- Gelato submission and child-item references survive connected-order splits, status updates, and partial cancellation.
- Gelato recovery targets only Gelato workflow identities; Lulu recovery remains pinned to existing Lulu identities.
- Disabling new Gelato dispatch leaves queued and submitted Gelato orders assigned to Gelato and recoverable there.
- User-facing notifications happen only after provider acceptance and durable state updates.
- A physical proof of the final book passes before any production cutover.
- Gelato's quote and draft response confirm the 32-page SKU count and processing of the independently validated 35-page PDF.
- Shipping selection comes from explicit config mapped to the order's saved shipping tier; missing policy never falls back to cheapest shipping. Quotes older than the internal 15-minute max age are refreshed before draft creation.

## Out of scope

- Replacing or renaming Lulu workflows, retiring Lulu, or switching live customer orders to Gelato.
- Revisions to story copy, character placement, cover art, or the breathing-exercise image.
- Selecting shipping prices or production defaults from historical sample quotes.
- Creating or paying for a production order during plan review.
- Changing Gelato account settings or creating API credentials during plan review.

## Risks and controls

- **Copied workflow drift:** Keep copies limited to provider-specific PDF and API behavior. Track shared renderer, job, and approval helpers as common code. Add export-diff checks that permit only deliberate Gelato changes.
- **Page-count ambiguity:** Require successful Gelato quote validation against the exact file before draft creation.
- **Duplicate or partial submissions:** Use unique references, provider-aware idempotency, durable pre-submit claims, and replay guards for single and grouped runs.
- **W4.1 order mapping:** Persist provider order and item references before notifying or marking every child complete.
- **Creative files remain in review:** Build test fixtures from the current frozen manifest. Do not treat test output as a final proof or enable live routing.
