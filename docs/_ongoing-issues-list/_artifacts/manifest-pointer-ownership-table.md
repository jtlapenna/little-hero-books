# Manifest pointer ownership table

**Created:** 2026-03-17  
**Purpose:** Phase 1 runtime contract cleanup deliverable for Book 2 prep. Document which runtime path owns each manifest/final-asset pointer on `orders`, which paths intentionally clear it, and what readers should assume about value shape.

## Phase 1 decision

For the active runtime, the `orders` manifest pointer fields are treated as **path-like pointers**, not as one exact string format.

That means a pointer may currently be stored as:

- a raw key like `book-mvp-simple-adventure/orders/<orderId>/manifests/2a-manifest.json`
- or a manifest API URL like `/api/manifests/...`
- or a fully-qualified app URL that still normalizes to the same key

Readers should normalize these values through `extractManifestKey()` / `buildManifestKeyCandidates()` in [order-paths.ts](/Users/jeff/Projects/little-hero-books/back-end/src/lib/order-paths.ts). Phase 1 does **not** require rewriting every writer to one string form; it requires stable ownership and stable derivation.

## Phase 1 conclusions

1. `manifest_2a_url` is no longer primarily a “missing writer” problem.
   The current primary writer in [workflow-2a-complete/route.ts](/Users/jeff/Projects/little-hero-books/back-end/src/app/api/webhooks/workflow-2a-complete/route.ts) resolves the exact per-item row, rejects group-key fallback, and throws if the update does not affect exactly one row.

2. Pointer loss is now expected mainly in explicit rewind/repair paths.
   The main intentional clearers are the regenerate endpoints plus `character-specs` regeneration and stale-pointer cleanup in the manifest repair routes.

3. Phase 1 standardization is a reader contract, not a string-format migration.
   The active runtime should keep normalizing pointer values through [order-paths.ts](/Users/jeff/Projects/little-hero-books/back-end/src/lib/order-paths.ts) and should not assume that every row stores an absolute URL vs a raw key.
