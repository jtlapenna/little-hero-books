# W1.5 Health Monitor - Issues and Fixes

## Issues Identified and Fixed

### 1. ✅ CRITICAL: Missing `continueOnFail` on HTTP Request Nodes

**Problem**: All HTTP Request nodes had `continueOnFail` removed, which means if any single order fails to update in Supabase, the entire workflow stops and no other orders are processed.

**Impact**: High - Could cause workflow to stop processing orders if one has a database error.

**Fix**: Restored `continueOnFail: true` to all 9 HTTP Request nodes:
- Stuck: Mark as Error
- Stuck: Log to Failed Orders
- Stuck: Mark for Manual Review
- Stuck: Schedule Retry
- Retry: Reset Status for Retry
- Orphaned: Recover: Create Manifest
- Orphaned: Recover: Schedule Retry
- Orphaned: Recover: Mark for Manual Review
- Orphaned: Recover: Reset Processing

### 2. ⚠️ IF Node False Paths

**Current Behavior**: 
- "Route by Work Type" sends ALL items to ALL three filter IF nodes
- Each item has a `_workType` marker ('stuck', 'retry', or 'orphaned')
- Only ONE filter will match (true path), the other two will have false outputs
- False paths are NOT connected, so items that don't match just stop processing

**Is This a Problem?**
- **Functionally**: No - each item only matches one filter, so false paths stopping is fine
- **Efficiency**: Yes - we're sending each item to 3 filters when we could route more efficiently
- **Clarity**: Yes - it's confusing that false paths aren't connected

**Recommendation**: 
- Current approach works but is inefficient
- Could optimize by using a Switch node or Code node to route directly
- For now, leaving as-is since it works correctly

### 3. ✅ General Error Orders Coverage

**Question**: How are general "error" orders (not stuck, retry, or orphaned) handled?

**Current Coverage**:
- **Stuck Path**: `execution_status = 'processing'` AND `started_at < 30 min ago`
- **Retry Path**: `execution_status = 'error'` AND `next_retry_at <= now()` AND `retry_count < 3`
- **Orphaned Path**: Via `get_orphaned_orders()` RPC function, which catches:
  - `execution_status = 'error'` AND `next_retry_at IS NULL` AND `retry_count < 3` → `error_no_retry_scheduled`
  - `execution_status = 'error'` AND `retry_count >= 3` → `error_max_retries_exceeded`
  - `execution_status = 'processing'` stuck → `processing_stuck_over_hour` or `processing_no_timestamp`
  - `execution_status = 'ready_for_processing'` not picked up → `ready_not_picked_up`
  - **NEW**: `execution_status = 'error_requires_manual_review'` AND `updated_at < 24 hours ago` → `manual_review_pending`

**Gap Identified**: 
- `execution_status = 'error_requires_manual_review'` orders were NOT being caught by orphaned orders function

**Fix Applied**:
- Updated `get_orphaned_orders()` SQL function to include `error_requires_manual_review` orders that have been waiting > 24 hours
- Updated orphaned classification logic to handle `manual_review_pending` reason
- These orders will now be included in the health monitor and routed to manual review

**Remaining Edge Cases**:
- `execution_status = 'error'` with `next_retry_at` in the future → Will be caught by retry path when time comes
- `execution_status = 'error_requires_manual_review'` < 24 hours old → Intentionally excluded (recently marked, waiting for human)
- Any other statuses → Should be in normal processing flow

## Summary

✅ **Fixed**: `continueOnFail` restored to all HTTP Request nodes  
✅ **Fixed**: `error_requires_manual_review` orders now included in orphaned orders (after 24 hours)  
⚠️ **Noted**: IF node false paths are inefficient but functionally correct  
✅ **Enhanced**: Detailed logging in merge node for better debugging
