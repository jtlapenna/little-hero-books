# Order Status System - Brainstorming & Proposal

## Overview
This document outlines the comprehensive status system for Little Hero Books orders, from intake through delivery.

## Main Order Status (Overall Order State)

### 1. **Order Intake & Processing**
- `new` - Order just received, not yet processed
- `queued` - Order queued for processing (waiting for workflow capacity)
- `processing` - Currently being processed by a workflow

### 2. **Internal Review Stages**
- `pending_base_review` - Waiting for Pre-Bria (base character images) review
- `pending_bg_removal_review` - Waiting for Post-Bria (background removal) review  
- `pending_assembly_review` - Waiting for Post-PDF (book assembly) review

### 3. **Revision States** (Stage-Specific)
- `revision_base` - Pre-Bria stage has flags, needs revision
- `revision_bg_removal` - Post-Bria stage has flags, needs revision
- `revision_assembly` - Post-PDF stage has flags, needs revision
- `revision_in_progress` - Revision requested, workflow regenerating

### 4. **Customer Approval** (if needed)
- `pending_customer_approval` - Waiting for customer to approve final book
- `customer_approved` - Customer has approved, ready for production
- `customer_revision_requested` - Customer requested changes

### 5. **Production & Fulfillment**
- `pending_print` - Approved, queued for print production
- `in_production` - Book being printed at Lulu
- `pending_shipping` - Printed, waiting to ship
- `shipped` - Book has shipped (tracking available)
- `in_transit` - Book in transit to customer
- `delivered` - Book delivered to customer
- `complete` - Order fully complete (all stages done)

### 6. **Error States**
- `failed` - Order processing failed
- `cancelled` - Order cancelled
- `on_hold` - Order temporarily paused

## Status Flow Diagram

```
new → queued → processing → pending_base_review
                                  ↓
                          [approved] → pending_bg_removal_review
                                  ↓
                          [approved] → pending_assembly_review
                                  ↓
                          [approved] → pending_customer_approval (optional)
                                  ↓
                          [approved] → pending_print → in_production
                                  ↓
                          pending_shipping → shipped → in_transit → delivered → complete
                          
[Any stage with flags] → revision_needed → revision_in_progress → [back to appropriate stage]
```

## Alternative: Simplified Status System

### Option A: Detailed (recommended)
- More granular, better visibility
- Clearer what stage order is in
- Easier to filter/sort by specific stage

### Option B: Simplified
- Combine review stages: `pending_review` (with stage metadata)
- Combine revision: `revision_needed` (with stage metadata)
- Fewer statuses, but requires metadata lookup

## Stage-Specific Status (reviewStages)

Each review stage (preBria, postBria, postPdf) maintains its own status:
- `pending` - Stage not yet reached / no assets available
- `in_progress` - Assets being generated by workflow
- `ready` - Assets available, waiting for review
- `in_review` - Under review by admin
- `approved` - Approved, ready for next stage
- `flagged` - Has flags, needs revision
- `revision_requested` - Revision requested, workflow regenerating

## Flag System Integration

Flags can be:
1. **Separate from status** - Status shows stage, flags show issues
   - Example: `pending_base_review` + `hasFlags: true`
   
2. **Integrated into status** - Status changes when flags exist
   - Example: `revision_base` instead of `pending_base_review`

**Recommendation**: Keep flags separate but show prominently in UI
- Status badge shows stage
- Flag badge shows "X Needs Attention" 
- When clicking, can see which stage(s) have flags

## Database Schema Considerations

### Supabase Orders Table
```sql
-- Main order status
status VARCHAR(50) NOT NULL DEFAULT 'new',
  -- Values: new, queued, processing, pending_base_review, pending_bg_removal_review,
  --         pending_assembly_review, revision_needed, pending_customer_approval,
  --         pending_print, in_production, pending_shipping, shipped, in_transit,
  --         delivered, complete, failed, cancelled, on_hold

-- Current workflow stage
workflow_stage VARCHAR(50),
  -- Values: order_intake, character_generation, base_review, bg_removal,
  --         bg_removal_review, book_assembly, assembly_review, customer_approval,
  --         print_production, shipping, delivery

-- Review stages (stored as JSONB or separate columns)
review_stages JSONB DEFAULT '{
  "preBria": {"status": "pending", "reviewedAt": null, "reviewer": null},
  "postBria": {"status": "pending", "reviewedAt": null, "reviewer": null},
  "postPdf": {"status": "pending", "reviewedAt": null, "reviewer": null}
}'::jsonb,

-- Flags tracking
has_flags BOOLEAN DEFAULT FALSE,
flags JSONB DEFAULT '{
  "preBria": 0,
  "postBria": 0,
  "postPdf": 0,
  "total": 0
}'::jsonb,

-- Production tracking
pod_order_id VARCHAR(100),  -- Lulu order ID
pod_status VARCHAR(50),     -- Lulu order status
tracking_number VARCHAR(100),
carrier VARCHAR(50),
shipped_at TIMESTAMP,
delivered_at TIMESTAMP
```

## Status Calculation Logic

The main `status` field should be calculated based on:
1. Current workflow stage
2. Review stage approvals
3. Flag presence
4. Production status

### Status Priority Rules:
1. If flags exist → `revision_needed` (or stage-specific revision)
2. If in production → `in_production`, `pending_shipping`, `shipped`, etc.
3. If waiting for review → `pending_[stage]_review`
4. If processing → `processing` or `queued`
5. Default → `new` or last known status

## Unified Display Layer (Admin-Friendly Labels)

To keep the admin panels simple while retaining backend fidelity, a helper maps every Supabase order into a small set of lifecycle labels. These labels drive the badges in the orders table, order detail header, stage tabs, and review queues.

| Display Label | When We Show It | Raw Signals (examples) | Notes |
| --- | --- | --- | --- |
| `New` | Order just arrived, workflows not started | `status` ∈ {`new`, `pending_processing`, `queued_for_processing`} | Covers the gap between intake and the first automation step |
| `Pending` | Automation or human review still in progress | `ai_generation_in_progress`, any `pending_*_review`, workflow steps 2A/2B/3 running | Any “not finished yet” internal work collapses here |
| `Approved` | All internal stages approved, proof not sent yet | `reviewStages.*.status === 'approved'` and `customerApprovalStatus` unset/false | Gives ops a checkpoint before triggering customer preview |
| `Proof Sent` | Customer preview link/token issued | `customerApprovalStatus === 'pending'` or `status === pending_customer_approval` | Used across list/detail/phase summary under “Customer Approval” |
| `Correction Requested` | Customer or reviewer flagged changes | `customerApprovalStatus === 'revision_requested'`, review stage `rejected/flagged`, or `flags.total > 0` | Any stage needing re-approval bubbles here |
| `Sent to Print` | Customer/admin approved; job handed to POD | `customerApprovalStatus === 'approved'`, `status` ∈ {`customer_approved`, `pending_print`, `in_production`, `pending_shipping`} or Lulu “processing” states | Covers production all the way up to shipping hand-off |
| `Shipped` / `Delivered` | Fulfilment status updates received | `status` ∈ {`shipped`, `delivered`, `completed`} or Lulu equivalents | Future shipping milestones can split here if needed |
| `Action Required` *(fallback)* | Hard failures or cancellations | `status` ∈ {`failed`, `action_required`, `cancelled`} | Surfaces in dedicated triage widgets/alerts |

### Helper Outputs
- `displayStatus` – string key (above) consumed by `StatusBadge`
- `phase` – `OrderPhase` bucket for the “Orders by Phase” widget
- `reasons` – optional metadata for logging/monitoring (e.g., which raw fields triggered the collapse)

All admin-facing surfaces import this helper so we only define the mapping once. The automation layer continues to set the granular `OrderStatus` enum values; the display map interprets them at render time and keeps the UI consistent.

## Customer Order Status Page (Friends & Family MVP)

**Route**: `littleherolabs.com/order-status/[orderId]` (Astro, SSR `prerender = false`)  
**Purpose**: Give customers a quick, trustworthy view of where their book is without exposing internal tooling.

### Layout Outline
1. **Header Card**
   - Order code (Amazon order ID if available)
   - Friendly title (`Adventure Compass for {ChildName}`)
   - Status badge + one-line explainer (“We’re printing your book now”)
   - Optional ETA if `shippedAt`/`deliveredAt` present

2. **Timeline**
   - Four milestone nodes (desktop horizontal, mobile vertical):
     1. `proof_ready` → Preview approved (shows `customer_approval_approved_at`)
     2. `print_submitted` → Sent to print (workflow 4 start)
     3. `in_production` → Printing in progress (Lulu status)
     4. `shipped` / `delivered` → Tracking info available
   - Each node displays state (complete/current/upcoming), timestamp, and short copy

3. **Detail Sections**
   - **What happens next**: dynamic copy keyed off main status
   - **Tracking panel**: carrier + tracking URL when available, fallback “We’ll email you when it ships”
   - **Need help?** CTA linking back to Amazon Message Center (with order ID prefilled)

## Questions to Resolve

1. **Customer Approval**: Do we need customer approval step, or is admin approval sufficient?
   - If yes, how does customer approve? (Email link? Portal?)

2. **Revision States**: 
   - Unified `revision_needed` or stage-specific (`revision_base`, etc.)?
   - Recommendation: Unified with stage metadata

3. **Lulu Integration**:
   - What statuses does Lulu API provide?
   - Can we get real-time updates or need polling?
   - What statuses map to our system?

4. **Status Transitions**:
   - Who/What triggers status changes?
   - Workflow webhooks? Manual admin actions? Automated based on conditions?

5. **Historical Tracking**:
   - Do we need status history/audit trail?
   - Or just current status with timestamps?

## Recommendations

1. **Use detailed status system** (Option A) for better visibility
2. **Keep flags separate** from status but show prominently
3. **Use status calculation function** that considers all factors
4. **Store stage statuses** in JSONB for flexibility
5. **Add status history** table if audit trail needed
6. **Map Lulu statuses** to our system when integration is ready

## Workflow Sync Runbook

To keep the human-review dashboard, customer preview flow, and n8n automations aligned, run this checklist whenever you are preparing a new integration test or notice mismatched statuses.

### 1. Reset the Reference Order

- Use the dev reset endpoint so you start from a clean Supabase and R2 state:
  ```bash
  curl -X POST http://localhost:3000/api/orders/TEST-ORDER-010/reset
  ```
- Confirm the response shows `status: "new"` and all `reviewStages.*.status` values are `pending`.

### 2. Execute Workflows 2A → 2B → 3 in Order

1. **Workflow 2A** (character generation)  
   - Trigger the n8n workflow (either manual run or cron) so it writes manifests and updates Supabase to `ai_generation_in_progress`.  
   - Make sure it calls the `/api/webhooks/workflow-2a-complete` endpoint so the review stage flips to `preBria.status = "ready"`.
2. **Workflow 2B** (background removal)  
   - Run the workflow and confirm it uploads the `2b` manifest, updates the Supabase row, and sets `reviewStages.postBria.status = "ready"`.  
   - Approve the Pre-Bria stage in the admin UI (or via API) so the workflow can proceed.
3. **Workflow 3** (book assembly)  
   - Execute the workflow so it produces `complete_book_<orderId>.pdf`, writes the `3` manifest, and updates Supabase (`status = "book_assembly_completed"`, `reviewStages.postPdf.status = "ready"`).  
   - Verify the webhook call (`/api/webhooks/workflow-3-complete`) succeeds.

> Tip: if you need to trigger an approval manually during testing, you can use  
> `curl -X POST http://localhost:3000/api/orders/TEST-ORDER-010/approve -d '{"stage":"preBria","status":"approved"}' -H 'Content-Type: application/json'`

### 3. Validate Supabase State

- Run these quick queries in Supabase SQL Editor (or via the REST API):
  ```sql
  select amazon_order_id,
         status,
         review_stages,
         manifest_2a_url,
         manifest_2b_url,
         manifest_3_url,
         final_book_url
  from orders
  where amazon_order_id = 'TEST-ORDER-010';
  ```
- Expected results after Workflow 3:
  - `status = 'book_assembly_completed'`
  - `review_stages.preBria.status = 'approved'`
  - `review_stages.postBria.status = 'approved'`
  - `review_stages.postPdf.status = 'ready'`
  - `manifest_*_url` fields populated
  - `final_book_url` or `complete_book_*` field populated

### 4. Validate R2 Assets

1. **Manifests**  
   - Download the `3-manifest` and confirm the entries reference the same keys Supabase exposes:
     ```bash
     curl -s http://localhost:3000/api/manifests/book-mvp-simple-adventure/orders/TEST-ORDER-010/manifests/3-manifest.json | jq '.pngGeneration'
     ```
   - Ensure the cover entry uses the same filename that the Post-PDF stage expects (`cover-spread.png` or `cover_preview.png`). Update the manifest or UI mapping so they match.
2. **Compiled PDF**  
   - Hit the PDF proxy endpoint; it should return 200 with a signed URL:
     ```bash
     curl -i http://localhost:3000/api/pdf/book-mvp-simple-adventure/orders/TEST-ORDER-010/complete_book_TEST-ORDER-010.pdf?format=json
     ```
   - If you see `PDF not available in this environment`, re-run Workflow 3 or check R2 credentials before attempting approval.

### 5. Walk the Review & Customer Flow

1. Approve Pre-Bria, Post-Bria, and Post-PDF in the admin UI (or via API) now that Supabase and R2 are in sync.
2. Trigger “Send Proof to Customer” and open the preview link generated by `/api/preview/generate-token`.
3. Submit a correction through the customer page, verify it appears in the admin “Order Status” card, then re-approve stages.
4. Complete the flow by selecting “Send to Print” and confirm `/api/orders/<orderId>/print` logs the placeholder Workflow 4 trigger.

### 6. Keep Restrictions Tight

- **Do not** set `NEXT_PUBLIC_ALLOW_APPROVAL_WITHOUT_PDF` or `ALLOW_APPROVAL_WITHOUT_PDF` to `true` in production. Only use these toggles in a dev sandbox when you explicitly do not have PDF access.
- Treat missing PDFs, missing manifests, or `reviewStages.*.status !== 'approved'` as signals to re-run the upstream workflow rather than bypassing the guardrails.
- Use the reset endpoint before every large integration test so stale feedback/revisions do not leak into the new run.

Following this runbook keeps Supabase, R2, the admin UI, and the customer preview workflow aligned without weakening production safeguards.
