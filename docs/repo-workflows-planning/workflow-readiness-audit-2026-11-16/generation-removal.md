## GR-01 — New pre-pose retry immediately hits the existing bootstrap barrier

Disposition: directly verified candidate; independent challenge pending. Severity P1 for the new recovery flow.

Trigger: an order enters canonical W2A, writes the empty 2A bootstrap, then SW0 fails (including depleted provider credit) before `resolve-pose-worklist`, leaving zero child jobs and no `orders.manifest_2a_url`. After cause resolution, the new `queueEarlyW2ARetry` accepts the order and queues ordinary routing.

Expected: the promised guarded retry resumes this eligible pre-pose run while preserving frozen W0 and its same-order bootstrap. Observed: `queueEarlyW2ARetry` verifies no jobs / no DB manifest pointer but does not account for persisted R2 bootstrap (`back-end/src/lib/w2a-failure-recovery.ts:114-130`). Router entry invariably reaches `Bootstrap 2A Manifest Stub` before `Execute SW0 - Base Character Gen`; `persistValidatedW2ABootstrapManifest` throws whenever conditional upload says object exists (`back-end/src/app/api/internal/w2a/bootstrap-manifest/route.ts:88-92`, HTTP409 at route end). `uploadW2ABootstrapIfAbsent` uses `ifNoneMatch:'*'` (`back-end/src/lib/books/w2a-manifest.ts:836-847`). There is no continue-on-error on the bootstrap HTTP node. Thus the retry can report queued while deterministically failing before any generation.

Proof: offline `probe.ts` calls the real persistence function with a public synthetic input and `uploadIfAbsent` returning false, verifies `W2ABootstrapExistsError`, and asserts the actual exported edge sequence preceding SW0. `probe.log` GR-01 passes. This uses a legacy synthetic input to isolate the persistence failure; configured bootstrap validation runs before the same unconditional existence barrier. No R2 writes occurred.

Smallest coherent repair: keep the conditional-create guard; permit deliberate reuse only after loading and verifying the existing bootstrap belongs to the exact frozen W0/order/book/hash and remains an empty bootstrap for a stopped admitted run with no child progress. Bind reuse to the current recovery claim; do not delete an arbitrary 2A manifest or generally ignore409. Test the real retry → router bootstrap path, mismatched/nonempty bootstrap and races. This defect applies even before partial-pose replay is considered.

## GR-02 — A denied child-job claim still flows into provider side effects

Disposition: directly verified candidate; independent challenge pending. Severity P1 (duplicate paid work, artifact writes without a new attempt).

Trigger: SW1/build-pose-input resolves an active job with an unexpired lease, or a nonclaimable terminal child job. W2B also hits this after force/removal reprocessing because its identity remains order/book/pose rather than source revision. Expected: only a newly claimed worker may submit; explicit verified replay may read existing artifacts. Observed: W2A returns `workflowClaimed:false,workflowReplay:null,workflowAttemptId:null` on claim refusal (`back-end/src/lib/workflow-jobs/w2a-pose-jobs.ts:474-491`). Its HTTP response still reports success; the SW1 export only branches on `workflowClaimed === false && workflowReplayReady === true` (`w2A-SW1-Pose_Generation.repo-centric.json:637`). False/no-replay routes to `Stamp Pose Index` and ordinary generation. Legacy succeeded jobs with a missing artifact take this same unsafe fallback. W2B returns false on claim refusal (`w2b-pose-jobs.ts:278-295`), yet `Build Bria Payload` passes its payload directly to `Bria Submit` (`w2B-sw1-single-pose.repo-centric.json:57,93`) without any claim check. No `workflowClaimed` consumer exists in that W2B export.

Proof: `probe.ts` uses the actual W2A/W2B claim functions with an injected in-memory repository following actual `canClaimWorkflowJob`; running/unexpired and failed W2A jobs return no claim/no attempt, and the exported IF condition evaluates false. W2B running/failed/succeeded cases likewise return no claim/no attempt; executing actual `Build Bria Payload` still produces its submit payload and the actual graph points directly to `Bria Submit`. All GR-02 probe cases pass. Provider endpoints were never contacted.

Repair owners: gate in backend response and both actual provider-consumer exports. Distinguish claimed, verified replay and held/conflict outcomes; stop before any binary/provider/overwrite action on held outcomes. A W2B source replacement or explicit retry needs an explicit revision/new attempt policy; do not merely add a gate and leave all legitimate reprocessing impossible. Claim enforcement also needs the replay-download failure branch to stop instead of silently regenerate without ownership. Focused test must execute real export branch conditions/code with denied claims and assert zero intercepted submit/upload calls.

## GR-03 — Configured partial-pose recovery cannot reuse successes, while inspection advertises generic replay

Disposition: recovery design gap directly established; preserve intentional safety hold. Severity P1 if partial configured resume is offered as ready; the trust hold itself is not a defect.

Trigger: configured order completes pose0 (or another pose), then stops before all required poses finish. Inspection's generic `resolveW2APoseWorkflowReplay` accepts succeeded uploadKey + artifact HEAD, and `safeToReplay` only requires incomplete jobs, active workflow and recovered original payload (`back-end/src/lib/w2a-recovery.ts:698-709,764-770`). Replay posts the original webhook payload (`:868-908`). Expected: either honest held recovery or verified reuse of successful configured poses with remaining jobs claimed safely. Observed: unchanged router entry first fails GR-01; if that barrier is deliberately relaxed, succeeded configured jobs throw `Configured W2A replay is on hold until a verified generation receipt is available` before artifact verification (`w2a-pose-jobs.ts:426-434`). Generic succeeded legacy replay does work after artifact existence. The failed/active jobs must also respect GR-02.

Proof: actual claim function rejects a succeeded configured synthetic job even with `replayArtifactExists` set true; callback is never reached. Same repository shape with legacy contract yields `reuse-succeeded-pose`. `probe.log` GR-03 passes. Current completion log only stores order/pose/uploadKey/generatedFileName/fileSize/correlationId/poseRefKey/baseCharacterKey; this is not a frozen recipe/base-content/provider receipt.

Safe recovery design evidence:

1. Do not remove the configured replay hold merely because an object exists. Bind reuse to frozen render snapshot/version, exact pose-reference and base identity/content, provider output identity and artifact digest/receipt; preserve legacy behavior separately.
2. SW0 has no generated-base cache admission. Its exported path loads reference images, creates a new provider base, and uploads the same canonical base key. Once bootstrap re-entry is enabled, SW0 will regenerate/overwrite before pose replay. Preserve or verify the original base for partial runs; restarting the base while reusing old pose art can mix character identity. `buildW2ABaseInput` uses the stable hash/book base key (`back-end/src/lib/books/w2a-base-input.ts:524`); fixed key identity does not prove same bytes.
3. `resolve-pose-worklist` attaches all required jobs; `enqueueWorkflowJob` returns existing rows without resetting status, attempts, inputs or output (`repository.ts:205-228`). Thus re-entry is not a clean slate. Queued jobs may claim; active unexpired jobs must hold; expired active jobs can reclaim; failed/succeeded/dead-lettered/canceled jobs are terminal under `claiming.ts`. Existing attempts are not closed by `claimAndStart*` when reclaiming an expired job. Never reset/delete succeeded or running rows indiscriminately.
4. QA regeneration currently deliberately bypasses configured replay for higher retryAttempt up to3 (`w2a-pose-jobs.ts:430-431`) but can reach terminal succeeded claim refusal. Enforcing GR-02 must include a coherent explicit retry attempt transition so this intended QA retry still works.
