# Unpaid queued fulfillment and scoped status engineering

## Design and boundaries

Normal W4/W4.1 still create held drafts; normal dispatch, conversion, status relay/polling, cancellation and customer delivery remain OFF. The authenticated engineering-automation endpoint accepts only a strict action and at most three unique, already stored exact conversion-authorization IDs. It cannot supply a replacement recipient, product, item, provider root, PDF or API key. The queue uses the existing atomic one-owner/one-send conversion core, with the existing short-lived no-payment attestation and SQL authority checks. This is an isolated queued executor, not approval to enable ordinary paid fulfillment.

Before any queue begin, the whole cohort must match the captured API-key fingerprint, submitted synthetic root/member/provider mappings, current exact child rows and frozen product/page descriptors, immutable artifact keys and SHA-256 bytes. Expired, closed and consumed entries are reported as skipped; busy/ambiguous acquisitions are never retried. Processing stops on unknown acquisition/outcome/persistence/closure, observed funding/production or a nonconverted result; later entries are explicitly not attempted. Automated responses omit private provider bodies and recipients. Queue completed is true only when every target is confirmed converted/closed, including previously closed converted targets; busy, expired or unresolved skips require review.

A simultaneous losing request previously closed the winning conversion's authorization through unconditional cleanup in both core and route. Cleanup now belongs only to a successfully acquired owner. Its service-role update changes only closed_at and filters exact ID, owner and currently open state, then confirms that same owner's persisted closure. A committed begin with a lost response remains unresolved and needs independent emergency closure, without retrying conversion. Observers never close active authorities. Existing unconditional emergency closure remains available to the protected operator. No database migration or privilege expansion is required.

Status-only execution permits closed, converted authorities after the same account/current-row/artifact checks; funding expiry does not grant another conversion. It reuses the canonical scheduled-candidate executor and mapped status-signal refresh helper. Provider IDs are allowlisted before fetch, including connected roots; the exact captured key is used, redirects are rejected, and no search, cancellation, broad candidate/outbox selection or delivery is reachable. Reloaded membership must retain its bound identity. Binding has a 60-second aggregate response budget; individual artifact reads retain their own bounded reader. Status execution has a 10-second deadline propagated through exact order reads, provider/file reads and store operations. An interrupted read never authorizes a send. A completed status execution can still require review; responses expose needsAttention/requiresReview for held or conflicting snapshots.

The shared normal poller retains its original selection, budget, recovery and delivery behavior. The normal relay retains authentication, global flag and mapped identity lookup. No scheduler or Gelato webhook subscription is created by this change. A controlled deployed invocation proves the executor, not actual recurring scheduling or external webhook delivery. Synthetic status signals must remain labeled as such.
